### 2.1 Work item 1 — Orchestrator-session user-tab via bash REPL hook

**Spec reference:** `sandbox/CONTEXT.md` §5.3 ("User-tab behavior") and §5.4
("The runtime hook in `spawnPane`"), per ADR 0002.

**Contract:**

- Every orchestrator workspace ships with exactly one `user` tab.
- The user tab's root pane runs `bash` (interactive REPL).
- `impl/pty/herdr-session.ts:HerdrSession.spawnPane` has a label-based guard
  at the top of the method that rejects any `targetTabId` whose tab label
  starts with `user-` (refuses to spawn any pane into the user tab).
- The orchestrator's system prompt carries the same rule in plain English
  ("Never spawn sub-orchestrators into a tab whose label starts with
  `user-`").
- The orchestrator reads the user tab's pane via `herdr pane read
  <user-pane>` to learn what the user typed; the orchestrator does **not**
  `send-text` into the user tab.
- When the orchestrator hands a sub-orchestrator the list of panes it
  should coordinate with, the user tab's pane id is **filtered out**.

**Current state in `test-2`:** the spec-2 work pinned the test (F7 in
`orchestration.spec.ts`) for the `spawnPane` guard. The runtime hook in
`impl/pty/herdr-session.ts:spawnPane` is implemented in spec-2 (the
`if (typeof opts.targetTabId === "string" ...)` block per CONTEXT.md §5.4).
**Action for `impl-2`:** verify the guard is wired end-to-end and add the
end-to-end test that the user tab's bash REPL is reachable, observable, and
isolated from the orchestrator's writes. Specifically:

- Add a live test in `impl/__tests__/live/orchestration.spec.ts` (or a new
  `user-tab-repl.spec.ts`) that:
  - Spawns the orchestration team, gets the user tab pane id from the
    `UserWorkspaceHandle`.
  - Issues `herdr pane read <user-pane>` from the orchestrator's pane and
    asserts it returns the bash prompt.
  - Types a `echo hello-from-user-tab` into the user tab via `send-text`
    (or via a fixture), waits, and asserts the orchestrator can read the
    output.
  - Confirms the orchestrator's `spawnPane(targetTabId=user-pane)` call
    throws the `spawnPane: refused — target tab is reserved` error.

**Estimated size:** ~80-120 lines of test code in `user-tab-repl.spec.ts` +
~5-15 lines of any minor wiring in `impl/pty/herdr-session.ts` if the
existing `spawnPane` guard has a gap.

### 2.2 Work item 2 — `spawn_fixer` lazy-spawn pathway

**Spec reference:** `sandbox/CONTEXT.md` §6.4 ("Adversarial challenges a
workstream; `spawn_fixer` is called") and the `spawnFixer` function
documented in `sandbox/docs/adr/0004-sub-orchestrator-tabs.md` and
`impl/orchestration/team-spawner.ts`.

**Contract:**

- `spawnFixer(workstream)` looks up the workstream in `/etc/surgical-fixers`
  (the registry written by `writeSurgicalFixersRegistryFromList`).
- If the workstream is not registered, `spawnFixer` throws.
- If the workstream is registered, `spawnFixer` spawns a readwrite pane
  (capability=readwrite) with the fixer name from the registry
  (`fixer-<workstream>`), returns a `paneId`, and the orchestrator
  hands the challenge text to the fixer pane via `send-text`.
- The lazy-spawn pathway means fixers are NOT pre-spawned in phase B; they
  are spawned on demand when the adversarial swarm emits a `block`
  challenge.

**Current state in `test-2`:** the spec-2 work added the
`/etc/surgical-fixers` registry and the `spawnFixer` runtime function. The
team-spawner.spec.ts has 20 tests covering the registry and `spawnFixer`; in
the yellow-phase run, 19 of those 20 passed and 1 timed out (T1 cold-start,
class (b) per `yellow-phase.md`). **Action for `impl-2`:** add a live test
that exercises the lazy-spawn pathway end-to-end:

- Add a live test that:
  - Spawns the orchestration team, gets the sub-orchestrator pane ids.
  - Logs a `block` challenge to the adversarial log (or calls
    `spawnFixer("scaffold_2")` directly to bypass the adversarial timing).
  - Asserts the fixer pane appears in `herdr pane list` with capability
    `readwrite` and a name like `fixer-scaffold_2`.
  - Asserts the registry entry is consumed / not re-spawned on a second
    call.

**Estimated size:** ~60-100 lines of test code in a new
`impl/__tests__/live/spawn-fixer-lazy.spec.ts`.

### 2.3 Work item 3 — Pane-0 invariant: real runtime + real exercising test

**Spec reference:** spec-2's `team-spawner.ts` JSDoc references
(`__tests__/live/team-spawner.spec.ts > pane-0 invariant`) and the
`assertSubOrchestratorIsLowestPane` function referenced in
`sandbox/docs/audit/yellow-phase.md` §3.

**Contract:**

- When a sub-orchestrator is spawned, the runtime checks that the
  sub-orchestrator's pane id is the lowest pane id in its tab.
- If the invariant is violated, the runtime emits a YELLOW warning
  (`liberty-pane-0-invariant`) to stderr / the challenge log.

**Current state in `test-2`:** the function `assertSubOrchestratorIsLowestPane`
**does not exist** in `impl/orchestration/team-spawner.ts` (a `grep`
confirms it). The JSDoc references in `team-spawner.ts` are
forward-references to a test that has not been written. The Phase 4 red
test (`sub-orchestrator-pane-invariant.spec.ts`) passes against the JSDoc
forward-references but does **not** exercise a real YELLOW warning. **This
is the YELLOW finding (c) from `yellow-phase.md` §3.**

**Action for `impl-2`:** close the gap. Two sub-tasks:

1. **Author the missing test** in
   `impl/__tests__/live/team-spawner.spec.ts` (or a new
   `pane-0-invariant.spec.ts`) that:
   - Spawns a sub-orchestrator, then injects a higher-id pane into the
     same tab via `herdr agent start` or `spawnPane`.
   - Captures the runtime's `console.warn` / stderr output and asserts it
     contains `liberty-pane-0-invariant`.
2. **Implement `assertSubOrchestratorIsLowestPane`** in
   `impl/orchestration/team-spawner.ts` if it is not present, and wire it
   into the sub-orchestrator spawn path so the warning fires when the
   invariant is violated.

**Estimated size:** ~40-80 lines of test code + ~10-25 lines of runtime code.
